# 恢复与事务修复记录（2026-09-19）

本记录对应 `tests/test_recovery.py` 的真实服务端回归测试。测试通过 TCP 执行 SQL，在临时数据库上执行正常关闭和 `SIGKILL`，不会读写用户数据库。

## 已复现并修复的问题

| 问题 | 修复前证据 | 修复方式 |
| --- | --- | --- |
| 重启后 LSN、事务 ID 从 0 重新分配 | 第二次启动产生 LSN 0，先前日志最大 LSN 为 6 | 分析完整日志时提取最大已使用编号，接受客户端前恢复两个分配器 |
| 创建边界落盘而缓冲日志丢失后，新 DML 被误当成旧表日志 | 保留 CREATE 元数据但截掉尚未持久化的 BEGIN/COMMIT，重启后插入的行在下一次恢复消失 | LSN 分配器同时以已保存的表创建边界为下限 |
| 旧未提交事务撤销覆盖后来的提交 | 第一次崩溃留下 INSERT，恢复后复用同一 RID 提交新行，再恢复时新行被删掉 | 按记录槽重建最终已提交状态，避免对新状态再次执行历史 loser 的物理撤销 |
| 已 ABORT 的脏页仍可能留在堆中 | 模拟 ABORT 已持久化、撤销页未刷盘，重启后仍能读到被取消的行 | 同时排除已中止和未提交事务的修改 |
| 断线事务永久保留锁和修改 | 断开持有写锁的连接，其他连接在两秒内一直收到 `abort` | 连接结束前回滚仍在事务表中的事务，再释放事务及连接内存 |
| 截断的日志尾部遮蔽后续提交 | 尾部添加 7 字节不完整日志，再提交新行并崩溃，新行恢复丢失 | 启动时截断并同步不完整尾部，随后追加从有效边界继续 |
| SQL 错误保留显式事务的修改 | 更新为 99 后执行非法 INSERT，仍读到 99 | 语义、语法和标准异常均返回错误并回滚当前整个事务 |
| 语法错误没有错误响应 | `select from;` 返回空字符串 | 将解析失败转换成明确 SQL 错误，并清理解析器缓冲和锁 |
| 多行唯一键修改的回滚可能冲突 | `1,2 -> 2,3` 的逐行索引撤销会遇到尚未撤销的键 | 先逆序还原所有堆记录，再根据还原后的堆重建受影响表的索引 |
| 自动提交先回应、后写提交日志 | 原服务端在 `write()` 成功后才执行 `commit()` | 提交日志持久化完成后才发送响应；提交/中止日志刷盘在释放锁之前 |

原测试还保留一个已有行为的回归：重启后的未提交 UPDATE 不应改变先前已提交值。此用例在修复前已经通过；它用于覆盖新的恢复实现，并不算新发现的失败。

## 恢复方法及边界

现有实现保留完整 WAL，未实现检查点、页 LSN、补偿日志（CLR）或完整 ARIES。此次修复采用与现有日志格式兼容的最终记录状态重建：

1. 读取完整有效日志，识别事务最终状态，并恢复编号分配器。
2. 对每个 `(表名, 页号, 槽号)`，取当前表创建边界之后第一条日志的修改前状态作为起点。
3. 按日志顺序只应用已提交事务的修改后状态；INSERT 为新值、UPDATE 为新值、DELETE 为空。
4. 将每个槽的最终状态写回堆，再从最终堆内容重建索引并刷出堆页。恢复应用前及最终刷盘前按实际 bitmap 重算每页记录数和空闲页链，处理文件头先于记录页保存的崩溃窗口。

第一条 INSERT 的起点是空槽，因此已中止或未提交 INSERT 的脏页会被删除。第一条 UPDATE/DELETE 的修改前镜像保留已有记录。旧 loser 与后来已提交事务复用 RID 时，后来的提交决定最终值。恢复中再次崩溃也可根据保留日志重新计算同一结果。

系统模块为每次 CREATE TABLE 保存 `.epoch` 创建边界。恢复忽略早于该边界的同名表日志，防止 DROP 后重建同名表时旧记录复活；已经删除且没有重建的表直接跳过。索引只在堆恢复完成后重建，避免当前索引与历史中间值之间的唯一键冲突。

存储及执行模块另行保证 INSERT 在修改槽内容前写入并同步 WAL，UPDATE/DELETE 先写日志再修改记录；日志写入处理短写并执行 `fdatasync`。事务提交在同步完成后释放锁、返回成功。普通 SQL 错误会中止整个显式事务，暂不提供语句保存点。

服务端 SIGINT/SIGTERM 处理只设置退出标志。监听循环关闭连接、等待所有工作线程完成事务回滚，然后刷日志并关闭数据库。TCP 按 NUL 分隔请求，缓存半包并保留合包中的后续请求；解析器缓冲和锁使用 RAII 清理。目录读写锁保护建表/删表/建索引/删索引与分析执行的交叉访问，DDL 在显式事务内被拒绝，修改已有表时仍需取得事务表 X 锁。

`tests/test_server.py` 的 4 个回归实际复现并验证了半包过早解析、合包丢失后续请求、SIGINT 退出前未写入 ABORT，以及 SELECT 发生锁冲突时 `abort` 响应缺少 NUL 结束符而导致客户端超时。关闭测试包含一个活动写事务与另一个已完成查询的连接，并在重启后验证未提交记录不存在。

## 验证命令

```sh
cmake --build build -j 6
python3 tests/test_recovery.py build/bin/rmdb -v
```

该脚本的 10 个测试覆盖重启编号、创建边界与丢失的缓冲日志、未提交 UPDATE、重复恢复与 RID 复用、断线回滚、残缺日志尾部、ABORT 脏页、SQL 错误、语法错误和索引键批量修改后的回滚。ABORT 脏页测试按现有二进制日志格式补入 ABORT，构造“ABORT 已落盘、撤销页尚未落盘”这一合法崩溃状态；创建边界测试保留 CREATE 元数据并截掉尚未落盘的日志后缀；其余场景由真实 SQL 和进程启停构造。

## 尚未实现或不能据此保证的能力

- 日志扫描和内存消耗随完整历史增长；没有日志压缩、检查点、后台恢复或 WAL 校验和。
- 旧版本数据库如果已经产生重复事务 ID，原日志本身无法可靠区分同号事务；新分配器阻止继续产生冲突，不能自动消除历史歧义。
- DDL 仍不是可回滚的事务操作，完整目录/元数据断电原子性未由本次进程崩溃测试证明。
- SIGKILL 测试覆盖进程崩溃，不等同于断电、磁盘损坏、部分页写入或文件系统故障注入。
- 有序关闭已覆盖上述实际连接场景；未进行无限连接、资源耗尽或任意系统调用失败的穷尽验证。
- 索引仍沿用项目现有内存有序结构及重建方式，没有在此实现完整持久化 B+ 树。
